# 开发脉络：从一个行为问题到双端实现

这份说明依据保留的历史方案、各版本源码、课程与竞赛材料整理。它描述开发方向怎样变化，不把文档计划当作已完成发布，也不推断缺少证据的日期、奖项或运营效果。

## 起点：先确定反馈机制，再确定技术载体

早期方向包含 Flutter + Supabase 的跨平台 App 方案，也留下 HTML/React 原型材料。这说明最初仍在探索载体；本仓库没有对应 Flutter 主工程，因此不将 Flutter 计入已交付技术栈。

贯穿后续版本的是同一个设计：用有限的日常选择生成相对评分，再把评分转成直观反馈。它试图降低行动记录与结果理解的成本。树木值与评分反向关联的设计，后来进入小程序和 Web 的具体实现。

## 聚焦：把小程序作为轻量使用入口

小程序方案将产品拆为用户、行为记录、评分、数据、游戏化反馈等模块。工程文档曾讨论传统后端与云开发两种路径，实际源码采用微信云开发。

这个阶段的价值，是让产品问题落实为页面与数据职责：身份从哪里来，记录保存到哪里，评分由谁计算，统计和森林怎样回看。后续扩展围绕这条核心链进行。

## 核心成形：v4、v5 与 v5.1

历史主工程中，v4 有 7 个注册页面、5 个业务云函数，v5 有 11 个页面、7 个业务云函数，v5.1 形成 13 个页面、8 个业务云函数。版本变化体现功能范围逐渐完整，不能单凭数量推断产品质量。

课程与计算机设计大赛材料以当时快照组织说明、演示和提交。提交材料中的 V5.0 是该场景的编号，不是今天公开 Web v5.0 的同义名称。竞赛参与是项目经历的一部分，本仓库不据此宣称获奖或真实用户成效。

## 继续迭代：小程序 v6.0 到 v6.7

2026 年 5 月的文档将关注点从比赛展示转向使用细节。后续版本保留 13 页骨架，围绕视觉反馈、种树动画、空状态与错误提示、统一返回约定、共享计算和离线同步继续整理。

v6.3 起出现 cloudfunctions/common 共享模块。各云函数部署目录还带有 common.js 副本，用于独立上传云函数；它们不是新增业务函数。公开版保留原同步脚本与检查入口。

v6.3–v6.6 的历史目录还混有嵌套旧副本。公开仓库选用直接位于版本根部的 v6.7，避免复制多个容易误认的工程入口。开发 v6.7 与讯飞杯提交源码在排除系统文件后逐文件一致，故不再同时公开一份重复副本。

## 另一条代码线：Web 从介绍产品走向独立应用

Web 早期探索过个人与企业方向。之后收敛到个人记录、数据、森林、成就、排行与资料，企业、团队和报表方向没有进入本次选定实现。

v3.0 起区分导览官网与 /app 应用入口。v3.2–v3.5 主要调整玻璃卡片、标题动画、固定背景和滚动展示；v4.0 组织成导览型官网与浏览器本地数据体验。

v4.0 到 v5.0 的关键变化，不只是页面视觉：它增加 FastAPI 后端、SQLite 数据库、JWT 身份与前端服务层，让保存与查询由后端按账号组织。公开源码保留这次转变后的前后端实现。

## 双端的关系：理念一致，数据各自独立

历史设想曾提出扫码登录、共用云数据与数据互通。但选定源码采用两套身份和存储：微信身份/云数据库与 Web 账号/JWT/SQLite，没有已实现的绑定同步层。两个端甚至保留不同的评分参数。

因此本仓库展示“同一产品的两种实现”，同时说明边界。开源整理没有新增互通机制，也没有把旧规划当作当前能力。

## 最后一次取舍：服务停止后，以历史作品公开

原文件夹同时保存了代码、学校材料、竞赛副本、参考资料、依赖、发布包、配置和运行数据。全部原样上传适合私有归档，却不适合作为公开展示的入口。

本次保留代表性双端与必要说明，省去旧版本重复、个人报名材料、用户数据库、私钥、本机工具记录、运营部署配置及未经证实的宣传数字。没有新增商业化、社交平台、碳交易或未来维护路线图。

公开的终点是把项目经历说明白：问题是什么，反馈机制为何这样设计，技术载体如何变化，代码实际做到哪一步，以及服务结束后留下了什么。
